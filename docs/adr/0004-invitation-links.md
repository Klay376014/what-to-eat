# Invitation links are `?invite=<token>` query links

Status: accepted (#6)

## Context

People join a trip through a link the organiser pastes into the group chat
(#1, stories 14 to 18). The link has to:

- open the app on whatever static host serves it, with no server rewrite
  rule;
- survive the Google sign-in round trip, which returns to the app's bare
  address (`auth.ts` sends `origin + pathname` as the redirect);
- sit beside `?day=` (the trip grid, #7) without either one knowing about the
  other;
- work without a router, which the app does not have.

## Decision

The link is the app's own address with one query parameter:
`https://<host>/<base>/?invite=<token>`.

- **Why a query parameter rather than `/invite/<token>`.** A path needs the
  host to serve `index.html` for a URL it has no file for. The Vite dev server
  does that, but GitHub Pages and most static hosts return a 404 page instead.
  A query parameter always reaches the one `index.html`.
- **Reading it.** `main.ts` calls `capturePendingInvite()`
  (`apps/web/src/invitations/pendingInvite.ts`) before the app mounts. It
  copies the token into `sessionStorage` and removes `invite` from the address
  with `history.replaceState`, leaving every other parameter alone.
  - `sessionStorage`, because it survives the sign-in round trip in the same
    tab and ends with the tab. A signed-out visitor who never signs in leaves
    nothing behind.
  - Removing it from the address means a reload does not join again, and the
    token is not left on screen.
- **Using it.** Once signed in, `InvitationGate` first says that joining
  shows the person's email to the others through calendar invitations, and
  offers joining without being a calendar guest (#14). On **Join trip** it
  calls `join_trip` with that choice and opens the joined trip; **Not now**
  joins nothing. Used, refused or declined, the token is then forgotten.
- **The token.** 32 random bytes from `gen_random_bytes`, as 43 unpadded
  base64url characters. It is generated by the database and cannot be chosen
  by a client.

### What the database enforces

All of it lives in `supabase/migrations/20260925100000_invitations.sql` and is
tested in `supabase/tests/database/`.

- A link expires 7 days after it is issued. A check constraint stops any row,
  the owner's included, from living longer.
- Only the current organiser can issue, read or revoke links. A revoked link
  stops working at once. People who already joined with it stay in the trip.
- Refusals name only what went wrong: `invitation_invalid`,
  `invitation_expired`, `invitation_revoked`, `trip_full`,
  `invitation_predates_departure`. None of them reveals the trip's id, name or
  organiser, and a stranger cannot read `invitations` to look a token up.
- Opening a link for a trip you are already in answers with the trip and
  changes nothing, even if the link has since expired or the trip is full.
- **A departed member comes back only with a link issued after they left.**
  Otherwise a removed member could walk back in with the link that first let
  them in.
- **8 current members at most.** A trigger on `trip_members` locks the trip's
  row and counts, so the limit holds on every path and under concurrent joins.
  Issuing a link for a full trip is refused too.
- **An organiser never leaves without handing over.** `leave_trip` refuses
  them, and `transfer_organiser` swaps the roles.
- **A deleted organiser account promotes the longest-standing current
  member.** The cascade from `auth.users` would otherwise leave a trip nobody
  can edit or delete (the question raised on #6).

## Consequences

- An invitation is a link, not a person. Anyone holding a working link can
  join, which is why links expire and can be revoked.
- If the app ever gains a router, `/invite/<token>` can be added as an alias.
  The query form must keep working, because links already sent will use it.
- The concurrency guarantee rests on the row lock. pgTAP runs in a single
  session, so it tests the limit itself, not the race.
